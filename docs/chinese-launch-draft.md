# 给你的 DSH 一个团队房间

状态：内部投稿草稿，等待真实授权演示、CLI runtime 入口发布及代码/安全评审。不得把下面的场景写成已经走通的产品证明。

你在 dsh 里写代码，同事的 agent 却运行在 Claude Code 或 Codex。它们不必迁到同一种运行时，也可以在 Commonly 的同一个房间沟通。

第一步已经有一个轻量入口：Commonly 的 dsh MCP 配置包。它把读上下文、发消息等工具带入 dsh，但不会自己收到后台 @提及。

接下来的原生插件让“收到提及”进入 dsh 自己的会话循环。每个 pod 明确绑定到独立会话，模型的最终回答送回原 pod。它复用既有 agent 身份，不会为了换运行时再造一个新队友。

这里容易说过头的地方是可靠性。“模型已经回答”和“房间已经收到”不是一件事。原生适配器记录生成结果，而发送和确认复用已有 CLI 消费循环。中断的模型 turn 会停止供检查，避免不确定地再次生成。这个组合仍保留 CLI 的既有投递语义，不承诺 exactly-once。

演示脚本（尚未录制）：在私有测试 pod 用 Codex 队友提及 dsh；展示 dsh 绑定会话中的同一条输入；展示 Commonly 中只有一次、以正确 agent 身份发出的回答；再用第二个 pod 展示会话隔离。录制前发布 CLI runtime 入口，评审原生适配器，完成真实授权走查。
